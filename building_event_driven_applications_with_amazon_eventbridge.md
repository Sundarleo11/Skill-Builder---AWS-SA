# 1. Introduction

**Amazon EventBridge** is a serverless event bus service that helps applications communicate using events.

It can receive events from:

- AWS services
- Custom applications
- SaaS applications
- Third-party applications

and route those events to appropriate targets.

A simplified architecture is:

```text
Event Source
     |
     v
Amazon EventBridge
     |
     v
Event Rule
     |
     +--------> Target A
     |
     +--------> Target B
     |
     +--------> Target C
```

The central idea is to build applications that respond to events rather than requiring every application to directly call every other application.

---

# 2. What Is an Event?

An **event** represents something that happened.

Examples:

- OrderCreated
- PaymentCompleted
- UserRegistered
- FileUploaded
- EC2 instance state changed
- Security finding created
- Customer subscription changed

Conceptually:

```text
Something Happens
       |
       v
     Event
       |
       v
EventBridge
       |
       v
Interested Application
```

An event usually contains information describing what happened, where it came from, when it happened, and the relevant data.

---

# 3. Event-Driven Architecture

An event-driven architecture (EDA) allows components to communicate through events.

Traditional tightly coupled architecture:

```text
Application A
      |
      v
Application B
      |
      v
Application C
```

Event-driven architecture:

```text
Application A
      |
      v
   EventBus
   /        v        v
App B     App C
```

Application A does not necessarily need to know how Application B or C is implemented.

This provides:

- Loose coupling
- Independent scaling
- Easier integration
- Better extensibility
- Event-based automation
- Fault isolation

---

# 4. Why EventBridge?

EventBridge is useful when applications need to react to events generated by different sources.

For example:

```text
AWS Services ----                  SaaS Application ---> EventBridge ---> Applications
                  /
Custom Events ---/
```

This allows a central event-routing layer to connect otherwise independent systems.


Important fields commonly include:

- `source`
- `detail-type`
- `detail`
- Event metadata

The exact structure depends on the event source and application.

# 15. Rules

A **rule** determines which events should be routed to which targets.

Conceptually:

```text
Event Bus
    |
    v
  Rule
    |
    +---- Match ---> Target
    |
    +---- No Match -> Ignore
```

Rules are one of the most important EventBridge concepts.

---

# 16. Event Patterns

An event pattern defines the events that a rule should match.

For example, conceptually:

```text
source = "com.example.orders"
detail-type = "OrderCreated"
```

Only matching events are routed to the associated target.

This allows applications to react selectively to events.

---

# 17. Example Event Pattern

Conceptual pattern:

```json
{
  "source": ["com.example.orders"],
  "detail-type": ["OrderCreated"]
}
```

This means the rule is intended to match events from the specified source with the specified detail type.

The actual pattern should be designed according to the event contract.

# 25. Loose Coupling

One of the biggest advantages of EventBridge is loose coupling.

Without an event bus:

```text
Order Service ---> Inventory
Order Service ---> Notification
Order Service ---> Analytics
```

The Order Service must know about multiple downstream systems.

With EventBridge:

```text
             +----> Inventory
             |
Order ---> EventBridge
             |
             +----> Notification
             |
             +----> Analytics
```

The producer publishes the event without directly managing every consumer.

# 33. Event Consumer Design

A consumer should:

- Validate incoming events.
- Process events safely.
- Be idempotent where necessary.

- Log useful information.

# 34. Idempotency

Events can potentially be delivered or processed more than once depending on the architecture.

Consumers should consider idempotency.

Example:

```text
Event
 |
 v
Consumer
 |
 v
Already Processed?
 |          |
Yes         No
 |          |
Ignore      Process
            |
            v
       Record Result
```

Idempotency helps prevent duplicate business effects.

# 44. Event Routing vs. Message Queuing

EventBridge and SQS solve different primary problems.

| Requirement | EventBridge | SQS |
|---|---|---|
| Event routing | Excellent | Not primary purpose |
| Event pattern filtering | Yes | Limited |
| Message queue | No | Yes |
| Buffering | Limited / different model | Excellent |
| Consumer decoupling | Yes | Yes |
| Long-running consumer processing | Often route to queue | Excellent |
| Event fan-out | Yes | Usually combined with SNS/EventBridge patterns |

A useful rule:

> **Use EventBridge to decide where an event should go; use SQS when you need a durable queue and consumer buffering.**

---

# 45. EventBridge vs. SNS

These services can overlap but have different strengths.

| Feature | EventBridge | SNS |
|---|---|---|
| Event filtering | Strong event pattern model | Filtering supported |
| AWS service events | Strong integration | Different notification model |
| SaaS/partner events | Strong use case | Different integration model |
| Event bus | Yes | Topic model |
| Pub/sub | Yes | Core capability |
| Event routing | Core capability | Fan-out/notification focus |
| Event-driven integration | Strong | Strong |

Choose based on the integration and messaging requirements.

---

# 46. EventBridge vs. Step Functions

These services also solve different problems.

| Requirement | EventBridge | Step Functions |
|---|---|---|
| Event routing | Yes | No |
| Event filtering | Yes | Not primary purpose |
| Workflow orchestration | No | Yes |
| Multi-step processing | Can start it | Core purpose |
| Branching workflow | No | Yes |
| Event-triggered automation | Yes | Can be target |
| Workflow state | Not primary purpose | Yes |

A common combination is:

```text
EventBridge
    |
    v
Step Functions
    |
    v
Multi-Step Workflow
```

# 47. Event-Driven Security

Security should be considered at every layer.

Important areas include:

- IAM permissions
- Event bus policies
- Target permissions
- Encryption
- Network controls where applicable
- Sensitive data handling
- Logging
- Monitoring
- Least privilege

A producer should have only the permissions it needs to publish events.

A rule should have only the permissions necessary to invoke its target.

# 48. Least Privilege

```text

   |

EventBridge
   |
   | Permission: Invoke target
   v
Target
```

Avoid broad permissions when narrowly scoped permissions are sufficient.

# 49. Sensitive Data

Events may contain business or customer information.

Before placing information into events:

- Determine whether it is necessary.
- Minimize sensitive fields.
- Protect event data appropriately.
- Consider retention implications.
- Avoid putting secrets into events.
- Control access to event buses and targets.

Event payloads can be copied to multiple destinations, so data minimization is important.

# 60. EventBridge Design Principles

Remember these principles:

1. **Publish facts, not commands where appropriate.**
2. **Keep producers loosely coupled to consumers.**
3. **Use rules to filter events.**
4. **Use targets according to processing requirements.**
5. **Design consumers for retries and duplicates.**
6. **Use DLQs and monitoring for failures.**
7. **Design stable event contracts.**
8. **Minimize sensitive data in events.**
9. **Use least privilege.**
10. **Monitor the complete event flow.**

# 61. Common Mistakes

## Mistake 1: Treating EventBridge as a General-Purpose Queue

EventBridge is primarily an event bus and routing service.

If you need durable message buffering and consumer queue semantics, consider SQS.

## Mistake 2: Sending Every Event to Every Consumer

Use event patterns to filter events.

## Mistake 3: Ignoring Duplicate Processing

Consumers should be designed with appropriate idempotency.

## Mistake 4: No Failure Strategy

Define retries, DLQs, monitoring, and alerting.

## Mistake 5: Poor Event Contracts

Events are interfaces between systems.

## Mistake 6: Putting Secrets in Events

Never use event payloads as a secret-storage mechanism.

## Mistake 7: Overloading Event Payloads

Only include information consumers need.

## Mistake 8: Tight Coupling Through Event Schemas

Avoid unnecessary dependencies on implementation-specific fields.

## Mistake 9: Ignoring Replay Side Effects

Replayed events can trigger business operations again.

## Mistake 10: Excessive Permissions

Use least privilege for event producers, buses, rules, and targets.

# 64. Example Architecture — Order Processing

```text
                 +------------------+
                 |  Order Service   |
                 +--------+---------+
                          |
                          | OrderCreated
                          v
                 +------------------+
                 |  EventBridge     |
                 +--------+---------+
                          |
              +-----------+-----------+
              |           |           |
              v           v           v
          Inventory   Notification  Analytics
```

### Flow

1. Customer creates an order.
2. Order Service publishes `OrderCreated`.
3. EventBridge receives the event.
4. Rules match the event.
5. Inventory receives the event.
6. Notification receives the event.
7. Analytics receives the event.

The Order Service does not need to directly invoke all three systems.

# 69. Knowledge Check Questions

### Question 1

What is Amazon EventBridge?

**Answer:** A serverless event bus service that routes events between AWS services, custom applications, SaaS applications, and other supported event sources and targets.

### Question 2

What is an event?

**Answer:** A representation of something that happened in a system or application.

### Question 3

What is an event bus?

**Answer:** A routing layer that receives events and sends matching events to configured targets through rules.

### Question 4

What is an EventBridge rule?

**Answer:** A configuration that defines which events should match and which targets should receive them.

### Question 5

What is an event pattern?

**Answer:** A set of matching conditions used by a rule to identify relevant events.

### Question 6

What is a target?

**Answer:** The destination that receives a matching event for processing.

### Question 7

Why is loose coupling important?

**Answer:** It allows producers and consumers to evolve, scale, and operate more independently.

### Question 8

What is a custom event?

**Answer:** An event generated by an application's own business logic rather than directly by an AWS service.

### Question 9

When would you use EventBridge with SQS?

**Answer:** When EventBridge should route an event and the downstream application also needs queue-based buffering and asynchronous processing.

### Question 10

When would you use EventBridge with Step Functions?

**Answer:** When an incoming event needs to initiate a multi-step workflow.

### Question 11

Why is idempotency important?

**Answer:** Because distributed event processing can involve retries or duplicate processing, and idempotency prevents unintended duplicate business effects.

### Question 12

What is a DLQ?

**Answer:** A dead-letter queue that can capture events or messages that cannot be successfully processed after the configured failure-handling behavior.

### Question 13

Why are event schemas important?

**Answer:** They define the contract between event producers and consumers and make integrations more predictable.

### Question 14

What is event filtering?

**Answer:** Matching events against rule patterns so that only relevant events are sent to specific targets.

### Question 15

Why should sensitive data be minimized in events?

**Answer:** Events may be routed to multiple systems and retained or replayed, increasing the potential exposure and governance impact of unnecessary sensitive information.

### Question 16

What is event replay?

**Answer:** Reprocessing previously archived events so consumers can process them again.

### Question 17

Why must replay be handled carefully?

**Answer:** Replayed events can trigger business operations again, so consumers should be designed for idempotency and downstream systems should be considered.

### Question 18

What is the difference between EventBridge and SQS?

**Answer:** EventBridge primarily routes events based on event patterns, while SQS provides managed message queuing, buffering, and consumer-oriented asynchronous processing.

```text
     Processing          Consumer

          Another Rule
                |

                |
```

The overall design principle is:

> **Publish meaningful events, route them with EventBridge rules, keep producers and consumers loosely coupled, and design every consumer for reliability, security, observability, and change.**
